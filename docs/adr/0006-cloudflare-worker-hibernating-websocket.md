# The gateway runs on a Cloudflare Worker, devices hold a hibernating WebSocket, and plugins ship from a GitHub registry

This replaces the device transport of decision record 0005 (one raw TCP connection from each Kindle to `DEVICE_PORT` 9990 on a gateway in Docker on a home server). What 0005 decided about the device side still holds: devices dial out and listen on nothing, a device is listed exactly while its connection is open, a Kindle connects only during a live session the owner starts, and the session rules (5 s, 15 s and 60 s reconnects, 15 minutes idle, 30% battery, `session_open` surviving a kill) are unchanged. Decision record 0004 also still holds: `/mcp` is stateless, issues no `mcp-session-id`, and answers `GET` and `DELETE` with 405; per-device state lives in the hub, not in an MCP session.

The old gateway only worked on the home network, and the device connection was the one thing that made hosting it elsewhere expensive. A Kindle in `always` mode holds its connection open around the clock, and a host that bills while a request or socket is open (Cloud Run, for example, about $93 a month at 1 vCPU and 0.5 GiB) bills for all of it. A Cloudflare Durable Object that accepts the socket through the WebSocket Hibernation API is evicted between messages and is not billed for duration while it sleeps, and the runtime answers the device's fixed 60 s ping (`{"type":"ping"}`, answered `{"type":"pong"}`) through `setWebSocketAutoResponse` without waking it. So the gateway is now `kindle-gateway-worker/`: a Worker that checks a bearer key and forwards, in front of one Durable Object named `hub` that holds every device's WebSocket on `GET /device` (device key) and serves the same stateless MCP tools on `POST /mcp` (agent key), on the Workers free plan behind a public HTTPS hostname. All JSON and image work runs in the object, because a free Worker gets 10 ms of CPU per request.

Measured with the emulator connected over `wss://` and no agent calls for 17 minutes (16:24 to 16:41 UTC on 2026-11-03, read from Cloudflare's GraphQL analytics): the object was billed 0.00484 GB-s of duration (37.8 ms of active time), 3 Durable Object requests (one every 5 minutes, which is the hub's own sweep alarm, `SWEEP_INTERVAL_MS` in `kindle-gateway-worker/src/hub.ts`, looking for silent sockets), and 0 inbound WebSocket messages, because every ping went to the auto-response. Projected to a day that is about 0.41 GB-s against a free allowance of 13,000 GB-s, and about 288 requests against 100,000. For comparison, two busy minutes running every tool including screenshots cost 4.6 GB-s. A 24 hour measurement with a real Kindle has not been taken yet.

Moving off the home server also removed `deploy_plugin`, which read plugin source from the home server's checkout. Plugins now reach devices only through the on-device installer: `scripts/publish.sh --github` attaches an archive to a GitHub Release and writes its `url`, `size` and `sha256` into `registry/index.json`, and the installer reads that manifest from the `main` branch by default. The checksum and the archive both come over https with the certificate and host name checked, so no server of ours sits in the install path.

Rejected: keeping the Node gateway and putting it on a billed-while-connected host; it works unchanged but costs the always-on price for a link that is idle almost all the time. Kept for now: `kindle-gateway/` on the home server as a LAN fallback that speaks raw TCP, until every Kindle has moved.
